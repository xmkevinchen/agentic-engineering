# AE 1.0 执行计划

> **Status: historical — a source proposal, not a plan.** This is one of the
> independent proposals written before AE v1's design was consolidated. It was
> never the specification, and the specification it fed into has itself since
> been archived. **Nothing here has authority over current work.** The set and
> how each source was judged: [`README.md`](../README.md). The current account of what AE
> is and where it is going: [`rebuild.md`](../../../rebuild.md).

> 草案 · 当前版本 0.14.2 · 2026-08-22
> 根：[`philosophy.md`](philosophy.md)　机制：[`design.md`](design.md)　实测：[`evidence.md`](evidence.md)
> 工作量：**S** ≈ 一次工作会话，**M** ≈ 一个 feature，**L** ≈ 需先单独讨论

## 顺序原则

不按"阶段硬屏障"排，按**依赖图**排。三阶段粗屏障被评审指出两处返工：在旧 AC 生命周期上验证仪器、随后又改掉它；以及采集器要在基线之后才建，形成死锁。

```
0. 先量，不改行为   →  1. 一条最小纵向切片  →  2. 接门与运行时纪律  →  3. 逐项替换删除
```

**只有一条真正不可交换**：破坏性删除排在最后。其余按依赖走，允许交叠。

**写退出条件的两条规矩**：

1. 退出条件只能指向**已存在、或本阶段内会被创造出来**的东西。不得引用后一阶段的产物，不得引用无人负责采集的指标。
2. 每条标注类型——〔能〕机制能工作，至少一次即可；〔常〕在常规工作中确实在用，需连续 3 个 feature。**1.0 达标要求〔常〕类全部满足**，否则"挑一个顺手的任务凑齐一次"就能宣布过关。

## 阶段 0 · 先量，不改行为

**要证明的**：我们有能力测量自己，且基线取自未被改动的系统。

| # | 工作 | 量 |
|---|---|---|
| 0.1 | 建采集器：中位 token/任务、**有效**人类打断次数、review finding actionable 率、SKILL.md 总行数、思考模板条数 | M |
| 0.2 | 建**读命中记录**（`design.md` §5 第 1 条）——判断知识层去留的唯一依据，现值为零 | S |
| 0.3 | 按 section 重切"思想 / 工具 / runtime 税"三类分布——现按文件划，税混在思想文件里 | M |
| 0.4 | 跑一次全量，记录每个脚本**历史上是否真的 fail 过**（删除前的保护档案） | S |
| 0.5 | **取基线**——0.1–0.3 全部就位之后 | S |

**退出条件**

| # | 类型 | 条件 |
|---|---|---|
| 1 | 〔能〕 | 五个指标各有一次成功采集，数值落盘 |
| 2 | 〔能〕 | section 级三类清单存在，可作前后对照 |
| 3 | 〔能〕 | 基线取样时间戳**早于**阶段 1 的任何提交 |

**撤退条件**：某指标无法自动采集且手工成本不可接受 → 该指标降为"不作为达标条件"，并在 1.0 达标判定中删掉对它的引用。**不允许留一个没有数据源的闸门。**

## 阶段 1 · 一条最小纵向切片

**要证明的**：一条新式 AC 能真正走完 `起草 → 确认 → 执行 → 判官 → 引用复核`，且非零退出码确实改变判断。

| # | 工作 | 量 |
|---|---|---|
| 1.1 | **recipe 执行的隔离与权限模型**——沙箱、超时、网络/密钥策略、工作目录限制、并发隔离、破坏性命令策略 | M |
| 1.2 | 契约 draft → 用户确认 → 不可变 revision + current pointer；生成业务口径的人类视图 | M |
| 1.3 | 三种证明模式落地；`collect-ac-evidence.py` 降级为退出码 runner（去 `KNOWN_PARSERS`、去 markdown 解析） | M |
| 1.4 | Evidence Ledger：append-only 事件 + `source_snapshot.manifest_digest`（执行前后各一次） | M |
| 1.5 | **隔离判官及其 verdict 契约**——何时调用、读哪些原始产物、verdict 如何进状态、失败/超时如何处理、引用如何交回仪器复核 | M |
| 1.6 | Gate 完成代数 + 唯一 finalize 入口（shadow mode，不接管现有路径） | M |
| 1.7 | `verify_by` 归入 AC 本体：改动它等同改动 AC，走 amendment | S |

**1.1 排在最前**：其余各项都要执行 agent 撰写的 recipe。没有隔离模型，那是一个任意命令执行面——recipe 由 agent 撰写、受仓库内容影响，不仅可能假绿，还可能改代码、改测试数据、改冻结文件、改验收脚本本身。本仓已有无意实例。

**退出条件**

| # | 类型 | 条件 |
|---|---|---|
| 1 | 〔能〕 | 一个真实 feature 上，每条 `command` 证明的 recipe 实际执行并返回退出码 |
| 2 | 〔能〕 | **一个非零退出码确实改变了判断**——Gate 在红码上没有给出 `finalize_eligible=true` |
| 3 | 〔能〕 | 该 feature 的契约经用户明确确认后才成为 revision；确认视图是业务口径 |
| 4 | 〔能〕 | 一次 source set 中途变化的执行被判为 `invalid` |
| 5 | 〔能〕 | 一条判官 verdict 的引用经仪器复核；解析不了的被丢弃并留痕 |
| 6 | 〔能〕 | 上述结论经**一条不依赖 Gate 自身的旁路**独立复核（自举悖论：不能用待修的机器证明它被修好了） |

**撤退条件**：跨 3 个 feature 累计 recipe **无法执行率 > 30%** → 停止，回到设计。那说明问题在"为什么写不出可执行的验收"，属契约起草层，不属证明层。

## 阶段 2 · 接门与运行时纪律

**要证明的**：边界有人守，指令到达层有纪律。

| # | 工作 | 量 |
|---|---|---|
| 2.1 | **验证义务四条**写进所有 agent 定义 + 断言边界（可以不回答，不可未验证而断言）；"未验证"改为必须携带的字段 | M |
| 2.2 | **Cast 棘轮**：项目事实只能在 Cast；可收窄不可放松；**消费方拒绝**（首要动作被覆盖时由被覆盖者报冲突） | S |
| 2.3 | 跨家族改为填座位：判官位/守门位交座位契约要的结构化产出，不再产出独立散文报告；产出以 `BACKEND: reached\|not-reached` 开头 | M |
| 2.4 | 覆盖守门：比较契约 Intent/Scope 与 AC 集合，指出漏项与越界；产出为"哪块需求无 AC 对应" | M |
| 2.5 | 编排两轴归位：评审、并行研究、判官、跨家族独立验证 → fan-out；讨论、发散、反对 → Teams | M |

**退出条件**

| # | 类型 | 条件 |
|---|---|---|
| 1 | 〔能〕 | **2.1 的实测验收**：抽 3 份 agent 实际产出，事实性断言均带可核对锚点；再抽 5 条锚点逐一核对全部成立。**不接受"义务文本已写进定义"作为证据** |
| 2 | 〔能〕 | 一条放松约束的 Cast 被消费方拒绝并报告 |
| 3 | 〔能〕 | 一次跨家族座位未达 backend，被第一行自述暴露，**并经 MCP 日志/transcript 外部确认** |
| 4 | 〔能〕 | 覆盖守门指出过一块无 AC 覆盖的需求（或报告覆盖完整，且该结论经埋入已知缺口的对照实验验证过一次） |
| 5 | 〔常〕 | 连续 3 个 feature：上述在常规流程中自然发生，不是为凑条件专门安排 |

**撤退条件**：若消费方拒绝的误报率高到打断正常工作 → 退回"警告但执行"，并记录拒绝率。

## 阶段 3 · 逐项替换删除

**要证明的**：删掉的是仪式与 runtime 税，思考模板一条没少。

**规则：按替代机制逐项删、逐项回归——不等整阶段做完一次性删。** `design.md` §9 的差异表是清单，每一项的替代物必须已在阶段 1/2 落地并经退出条件验证。

| # | 工作 | 量 |
|---|---|---|
| 3.1 | 删形态匹配脚本（约 27 个），保留 6 个零知识仪器 | M |
| 3.2 | 删它们强制的散文（两者是同一件东西的两半） | M |
| 3.3 | `agent-teams` + `agent-selection` 收缩——目标行数由 0.3 的 section 级清单定，**不预设数字** | M |
| 3.4 | 四份并行状态记录合并为单一 ledger | M |
| 3.5 | `.ae/graph` → `.ae/knowledge`（**1.0 发布前必须完成**——用户数据，之后改要带迁移） | S |

**退出条件**

| # | 类型 | 条件 |
|---|---|---|
| 1 | 〔能〕 | SKILL.md 总行数显著下降，而**思考模板条数不减少**（以 0.3 清单前后对照） |
| 2 | 〔能〕 | 全套测试仍绿，**且绿不是靠删除测试达成的**——被删脚本逐一对照 0.4 的历史 fail 档案 |
| 3 | 〔常〕 | 连续 3 个 feature：阶段 1/2 的退出条件仍然成立 |

**撤退条件**：删除后出现本该被拦截的缺陷 → 按 0.4 档案定位到具体脚本，**单独恢复它**，不回滚整个阶段。

**已被实测证伪的两条压缩估计**（不得再作为目标）：通信/生命周期机械"可压到 60 行"——后台座位产出不自动回流，收结果是刚需；跨家族管道"大部分失去存在理由"——一份手写 spawn prompt 当场踩中它防的坑。**纸面判为"税"的东西，有一部分在当前 runtime 上是刚需。**

## 1.0 达标判定

不能只靠"活干完了"。全部满足才发：

1. 阶段 0–3 的退出条件全部满足，**含全部〔常〕类**
2. `.ae/knowledge` 改名落地（3.5）
3. **基线证明没有退化**：任务成功率不低于基线、中位 token 不高于基线，**样本不少于 3 个 feature**
4. **知识层读命中 > 0**
5. **兼容面写进 README**：`/ae:*` 调用名与参数形态、`pipeline.yml` 字段、`.ae/` 结构与产物格式、agent 名——此后改动需主版本号
6. **回归逃逸率设发布后观察窗**：按定义只能在发布后观察，故不作发布当天闸门，而是**1.0 发布后 3 个月的复核条件**；高于基线则回溯定位到具体删除或改动项

---

## 回滚

- **阶段 1 是唯一不可逆点**——它改变契约与证据的语义。已有 feature 按 legacy 处理，不回溯
- 阶段 2 的门与纪律可逐个关掉，不影响阶段 1
- 阶段 3 是删除，靠 git 恢复 + 0.4 档案定位
- 3.5 改名一旦发布即进入兼容面，之后只能带迁移

**若阶段 1 撤退条件被触发**（recipe 无法执行率 > 30%），整个 1.0 的前提需重新审视——那说明问题不在证明机制，在起草层写不出可执行的验收。
